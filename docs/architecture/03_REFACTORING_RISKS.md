## 2. Risk 1: JNI Linkage Breakage (`UnsatisfiedLinkError`)

### The Hazard
C++ native functions use static symbols generated by JNI mangling rules:
`Java_com_neonsong_app_playback_NativeAudioEngine_initAudioEngine`
If `NativeAudioEngine.kt` is moved from package `com.neonsong.app.playback` to a new modular package such as `com.neonsong.app.core.audio`, the JVM will fail to locate the symbol at runtime, causing an immediate crash when audio playback initializes.

### Mitigation Protocol
1. **Low-Level Bridge Lock:** Keep the exact package declarations for the 5 low-level bridge files:
   - `com.neonsong.app.playback.NativeAudioEngine`
   - `com.neonsong.app.playback.NativeAutoMixEngine`
   - `com.neonsong.app.playback.NativeAutoDJEngine`
   - `com.neonsong.app.playback.eq.ParametricEqNative`
   - `com.neonsong.app.data.lossless.NativeSecrets`
2. **Adapter Layer:** Introduce high-level Kotlin contracts (`core/audio_api/AudioEngine.kt`) that wrap these low-level bridge classes. Modular features only interact with the contract, while the bridge remains permanently locked at its JNI-compliant package.

## 3. Risk 2: Real-Time Audio Thread Jitter & Dropouts

### The Hazard
The Oboe audio stream runs an ultra-low latency real-time thread (`onAudioReady`).
If any code path invoked from this thread performs:
- Heap allocation (`new`, `malloc`, Kotlin object creation, boxing, `String` formatting)
- Thread synchronization (`synchronized`, `std::mutex`, semaphores, `Object.wait()`)
- JNI upcalls back to Java/Kotlin
- File I/O or network I/O
- Coroutine dispatch or GC-triggering operations

The OS audio subsystem will suffer buffer underruns, producing audible clicks, pops, or complete audio dropout.

### Mitigation Protocol
1. **Strict Buffer Isolation:** C++ audio callback consumes exclusively from lock-free SPSC ring buffers (`AudioRingBuffer.h`) using `std::atomic<size_t>` with `memory_order_acquire` / `memory_order_release`.
2. **DSP Pre-Allocation:** All filter coefficients, WSOLA window buffers, and SoXR resampler state are allocated during engine initialization (`initAudioEngine`). Zero allocations occur per audio block.
3. **No Upcalls:** The native engine posts telemetry or end-of-track notifications asynchronously via lock-free status queues polled by the playback service, never via synchronous JNI callbacks from the audio thread.

## 4. Risk 3: Dual ExoPlayer & Deck Switching Glitches

### The Hazard
Neon Song uses a Dual ExoPlayer design (Deck A and Deck B) routed into a custom `NativeProcessingAudioSink`. During track transitions, crossfade, or AutoDJ handoff, both players may run concurrently. Inappropriate state changes or uncoordinated release calls can cause race conditions, duplicate playback, or audio corruption.

### Mitigation Protocol
1. **Contract Encapsulation:** All player coordination is encapsulated inside `features/player/domain/DeckManager.kt` implementing `PlaybackController`.
2. **Atomic Volume Ramping:** Crossfading uses equal-power curves calculated natively in C++ (`CrossfadeMixer.cpp`), preventing volume clipping when combining dual 32-bit float streams.

## 6. Risk 5: Room Database Schema Incompatibility

### The Hazard
Neon Song maintains 5 Room entities:
- `SavedPlaylistEntity`
- `SongPlayStatsEntity`
- `DownloadedTrackEntity`
- `ArtworkCacheEntity`
- `RecommendationExclusionEntity`

Altering table names, column names, or type converters will trigger SQLite `IllegalStateException: Room cannot verify the data integrity`.

### Mitigation Protocol
1. Keep Room entities and DAOs in `core/database/` with zero schema changes.
2. Verify Room schema checksum matches the current production schema version.
